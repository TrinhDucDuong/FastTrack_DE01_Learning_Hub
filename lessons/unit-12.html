Real-time Data Streaming on Azure

Xử lý event liên tục với partition, checkpoint và delivery semantics.

Event HubsStreamingWatermarkCheckpoint

Trong bài này

1. Streaming không có nghĩa là "ngay lập tức"

Streaming xử lý luồng event liên tục với latency thấp hơn batch. Trước khi chọn, phải xác định SLA: vài giây, vài phút hay một giờ. Nếu business chấp nhận hàng giờ, batch thường đơn giản và rẻ hơn.

Producers -> Event Hubs -> Stream processor -> Bronze/Silver -> Serving
                  \-> checkpoint / monitoring / dead-letter

2. Event Hubs mental model

  • Namespace: container quản lý cho các event hub.
  • Event hub/topic: append-only stream.
  • Partition: log có thứ tự; thứ tự chỉ được đảm bảo trong từng partition.
  • Partition key: quyết định event vào partition nào; cùng key thường giữ ordering.
  • Offset/sequence: vị trí event trong partition.
  • Consumer group: một góc nhìn độc lập của cùng stream cho một ứng dụng tiêu thụ.
  • Retention: event chỉ được giữ theo thời hạn cấu hình; data lake mới là nơi lưu dài hạn.

Partition tăng parallelism nhưng key lệch có thể tạo hotspot. Số consumer instance hữu ích bị giới hạn bởi số partition trong consumer group.

3. Delivery semantics

  • At-most-once: có thể mất event, ít duplicate.
  • At-least-once: không muốn mất nhưng có thể nhận trùng; rất phổ biến.
  • Exactly-once effect: thường đạt ở kết quả nghiệp vụ bằng source replay + checkpoint + dedup/idempotent sink, không chỉ nhờ một nhãn cấu hình.

Thiết kế event_id hoặc business key + version/timestamp để deduplicate.

4. Event time và processing time

  • Event time: lúc sự kiện thực sự xảy ra.
  • Processing time: lúc hệ thống xử lý.
  • Late event: đến sau khoảng mong đợi.
  • Watermark: ngưỡng hệ thống chờ event muộn trước khi dọn state/finalize window.

Window phổ biến: tumbling (không chồng), sliding (chồng), session (theo khoảng hoạt động). Watermark càng rộng càng bắt được late data nhưng giữ state lâu hơn.

5. Structured Streaming

Spark Structured Streaming dùng DataFrame API cho stream:

events = (
    spark.readStream.format("eventhubs")
         .options(**event_hubs_config)
         .load()
)

query = (
    transformed.writeStream
      .option("checkpointLocation", checkpoint_path)
      .outputMode("append")
      .start(output_path)
)

Checkpoint phải ở durable storage, tách theo query và được bảo vệ quyền truy cập. Xóa checkpoint có thể làm mất tiến độ hoặc replay dữ liệu tùy cách start.

6. Schema evolution và poison message

  • Event có version/schema contract.
  • Thêm nullable field thường dễ tương thích hơn đổi tên/đổi type.
  • Validate compatibility trước release producer.
  • Record không parse được đi quarantine/dead-letter cùng error reason và metadata.
  • Không để một poison message chặn cả partition vô thời hạn.

7. Monitoring

Theo dõi đồng thời:

  • Ingress/egress throughput và throttling.
  • Consumer lag theo partition.
  • Event age/freshness.
  • Parse error, duplicate, dead-letter volume.
  • Processing rate, batch duration, state size, checkpoint error.
  • Sink latency và failure.

"Job vẫn running" không có nghĩa là healthy. Lag tăng hai giờ có thể do compute thiếu, skew partition, downstream chậm hoặc throttling.

8. Recovery và replay

  • Event retention phải dài hơn thời gian phát hiện + phục hồi dự kiến.
  • Capture/raw landing giúp replay ngoài retention của stream.
  • Lưu source offset/checkpoint và mapping tới run_id.
  • Sink phải idempotent khi replay.
  • Viết runbook cho checkpoint corrupt, credential hết hạn, schema incompatible và lag tăng.

9. Bài thực hành

Thiết kế clickstream:

  1. Chọn partition key và giải thích ordering/skew.
  2. Mỗi event có event_id, event_time, schema_version.
  3. Tạo revenue window 5 phút với watermark 15 phút.
  4. Quarantine JSON lỗi.
  5. Ghi raw để replay và Silver đã deduplicate.
  6. Đề xuất alert cho lag, zero ingress và dead-letter spike.

10. Checklist

  • SLA latency thực sự cần streaming.
  • Partition key không tạo hotspot.
  • Có event ID, schema version và event time.
  • Consumer xử lý duplicate/out-of-order/late event.
  • Checkpoint durable; sink idempotent; có đường replay.

Tài liệu chính: Azure Event Hubs scalability, Spark Structured Streaming.

11. Thiết kế event contract

{
  "event_id": "evt_01...",
  "event_type": "order.completed",
  "event_version": 2,
  "occurred_at": "2026-09-22T03:10:04Z",
  "producer": "order-service",
  "aggregate_id": "order_123",
  "payload": {"customer_id": 10, "net_amount": 120.50}
}

Envelope chuẩn giúp trace, deduplicate, route và evolve schema. Event là fact đã xảy ra; tên ở past tense giảm nhầm với command.

12. Partition key trade-off

Chọn order_id giữ thứ tự event của cùng order và phân phối tương đối đều. Chọn country có ít key dễ hotspot. Không có global ordering khi nhiều partition; nếu business cần global order, chi phí/throughput thay đổi lớn và cần xem lại requirement.

13. Consumer group bằng ví dụ

Fraud detector và lake ingestion cần đọc cùng stream độc lập → hai consumer groups. Scale-out các instance của cùng ứng dụng → cùng consumer group để chia ownership partition. Tạo consumer group mới không tự đọc vô hạn lịch sử ngoài retention.

14. Watermark worked example

Window 5 phút, allowed lateness 15 phút:

  • Event time 10:03 đến lúc 10:04: vào window 10:00–10:05.
  • Event time 10:03 đến lúc 10:14: late nhưng còn trong policy, aggregate được update.
  • Event time 10:03 đến sau watermark vượt window + 15 phút: bị drop/route tùy engine và output mode.

Policy phải dựa phân phối lateness đo được và nhu cầu sửa báo cáo, không chọn tùy ý.

15. Exactly-once cần nhìn end-to-end

Checkpoint có thể đảm bảo engine biết offset nào đã xử lý, nhưng sink/API bên ngoài vẫn có thể ghi trùng khi crash giữa write và checkpoint. Cách đạt hiệu ứng exactly-once:

  • Transactional/idempotent sink.
  • Deterministic event ID/business key.
  • Dedup state hoặc unique constraint.
  • Atomic commit giữa progress và output nếu platform hỗ trợ.

Luôn mô tả boundary guarantee thay vì nói toàn hệ thống "exactly once".

16. Backpressure và lag

Khi input rate > processing rate, lag tăng. Điều tra:

  1. Có partition hotspot không?
  2. Processing có chậm do state/shuffle/UDF không?
  3. Sink có throttle/latency không?
  4. Compute có đủ và autoscale kịp không?
  5. Retention còn đủ thời gian recovery không?

Scale consumer nhiều hơn số partition không tăng parallelism hữu ích trong consumer group.

17. Câu hỏi có đáp án

  1. Offset có phải event ID? Không; offset là vị trí trong partition, event ID phục vụ identity/dedup nghiệp vụ.
  2. Một partition có ordering với partition khác không? Không có global ordering guarantee.
  3. Streaming thay batch hoàn toàn không? Không; backfill/reconciliation thường vẫn dùng batch.
  4. Checkpoint có nên đặt local disk worker? Không cho production durable recovery; worker mất sẽ mất progress.
