Batch Data Processing on Azure

Orchestrate batch với watermark, CDC, quality gate và backfill.

ADFBatchCDCBackfill

Trong bài này

1. Batch pipeline là gì?

Batch xử lý một tập dữ liệu hữu hạn theo lịch hoặc sự kiện: mỗi giờ, mỗi ngày hoặc khi file đến. Mục tiêu không chỉ là copy thành công mà còn đúng dữ liệu, rerun an toàn và trace được.

Source -> Ingest -> Bronze -> Validate/Transform -> Silver -> Gold -> Publish
              \-> audit, metrics, alert, quarantine

2. Azure Data Factory (ADF) mental model

  • Pipeline: nhóm hoạt động thành một workflow.
  • Activity: một bước copy, transform, lookup, execute...
  • Dataset: mô tả shape/location dữ liệu dùng bởi activity.
  • Linked service: thông tin kết nối tới data store/compute.
  • Integration Runtime (IR): hạ tầng kết nối/di chuyển/dispatch compute.
  • Trigger: lịch, tumbling window hoặc sự kiện khởi chạy.
  • Parameter/variable: tái sử dụng pipeline theo bảng/ngày/môi trường.

ADF chủ yếu orchestration/data movement; transformation lớn có thể giao cho Spark/Databricks/SQL engine. Microsoft hiện cũng định hướng người mới xem Data Factory trong Microsoft Fabric; vẫn cần hiểu ADF cho hệ thống hiện hữu.

3. Full load và incremental load

  • Full: đơn giản nhưng tốn thời gian/chi phí, phù hợp bảng nhỏ.
  • Watermark: lấy record có updated_at mới; phải xử lý cùng timestamp và late update.
  • CDC: đọc insert/update/delete từ change log; cần quản lý offset và retention.
  • Partition/file discovery: lấy folder/file mới; cần manifest và chống file trùng/dở dang.

Watermark pattern:

  1. Đọc last_successful_watermark.
  2. Chốt upper_bound cho run hiện tại.
  3. Extract (last - lookback, upper_bound].
  4. Merge/deduplicate target.
  5. Validate và commit.
  6. Chỉ sau đó cập nhật watermark thành upper_bound.

4. Idempotency và partial failure

  • Mỗi run có run_id, batch_id, input range.
  • Copy raw vào path deterministic hoặc ghi manifest trạng thái.
  • Transform ghi staging trước, validate rồi publish/merge.
  • Không đánh dấu thành công nếu chỉ một phần target hoàn tất.
  • Nếu chấp nhận partial success, ghi rõ record thành công/lỗi và cơ chế replay đúng phần lỗi.

Retry chỉ dành cho lỗi transient. Dùng exponential backoff + giới hạn retry; sai schema/credential không hết hạn thì cần fail rõ và alert.

5. Metadata-driven pipeline

Thay vì copy-paste 100 pipeline, dùng control table:

source_table | target_path | load_type | watermark_col | enabled
orders       | bronze/...  | watermark | updated_at    | true
customers    | bronze/...  | full      | null          | true

Pipeline đọc metadata, loop từng entity và truyền parameter. Lợi ích: nhất quán, mở rộng nhanh; rủi ro: control table trở thành thành phần quan trọng nên phải validate, version và audit.

6. Data quality gates

Trước và sau mỗi layer kiểm tra:

  • Schema/required columns.
  • Row count và distinct business key.
  • Null/duplicate/range/domain.
  • Control total như tổng amount.
  • Freshness và expected volume.

Zero row không luôn là thành công. So sánh với baseline và business calendar trước khi alert.

7. Failure zones và runbook

Runbook phải trả lời: bước nào hỏng, dữ liệu nào bị ảnh hưởng, rerun có an toàn không, ai cần được báo.

8. Bài thực hành

Thiết kế pipeline ADF nạp orders hàng ngày:

  1. Parameter process_date và run_id.
  2. Copy incremental vào Bronze.
  3. Kiểm tra source/landing count.
  4. Gọi transform Silver/Gold.
  5. Ghi audit table và watermark.
  6. Alert khi fail, zero records hoặc trễ SLA.
  7. Backfill một ngày mà không tạo trùng.

9. Checklist

  • Khoảng dữ liệu của mỗi run xác định rõ.
  • Watermark/offset chỉ commit sau khi toàn pipeline thành công.
  • Rerun/backfill đã được thử.
  • Bad data được quarantine, không làm mất toàn bộ batch nếu policy cho phép.
  • Có metric, alert, lineage và owner.

Tài liệu chính: Giới thiệu Azure Data Factory.

10. Integration Runtime chọn thế nào?

  • Azure IR: data movement/dispatch trong cloud và public endpoints hỗ trợ.
  • Self-hosted IR: kết nối on-prem/private network; chính máy/VM này cần capacity, patch, HA và monitoring.
  • Azure-SSIS IR: chạy SSIS package khi migration/use case cần.

IR là data path quan trọng. Bottleneck có thể nằm ở source, network, IR hoặc sink; scale IR không chữa source query chậm.

11. Control flow production

Lookup config
 -> ForEach entity (bounded parallelism)
   -> Get source watermark/upper bound
   -> Copy to staging/Bronze
   -> Validate count/checksum
   -> Transform Silver/Gold
   -> Quality gate
   -> Publish + update watermark
 -> Summary audit + alert

ForEach concurrency phải tôn trọng giới hạn source/sink. Một pipeline chạy nhanh hơn nhưng làm production DB timeout là thất bại.

12. Parameter, variable và expression

  • Parameter là input của pipeline/dataset, thường immutable trong run.
  • Variable là state nội bộ pipeline; cẩn thận khi thay đổi trong parallel loop.
  • Dynamic content tạo path/query, nhưng cần whitelist/escape để tránh tên object không hợp lệ hoặc SQL injection khi build query.

Ví dụ path deterministic:

bronze/orders/ingestion_date=2026-09-22/run_id=<run-id>/

13. Copy performance checklist

  1. Đo source query riêng và kiểm tra index/partition.
  2. Xem bytes/rows, throughput và duration từng activity.
  3. Kiểm tra parallel copy/partition option phù hợp.
  4. Kiểm tra sink throttling, file count và network path.
  5. So sánh DIU/IR capacity trước và sau thay đổi.

Không tối ưu bằng cách tăng parallelism vô hạn; có thể tạo too many small files hoặc rate limit.

14. Backfill design

Backfill là workload hạng nhất, không phải sửa tay:

  • Input from_date/to_date hoặc list interval.
  • Cùng transformation code với daily run.
  • Pool/concurrency riêng để không tranh tài nguyên production.
  • Output overwrite/merge đúng partition.
  • Audit link giữa backfill run và original intervals.
  • Re-refresh downstream đúng phạm vi.

15. Failure walkthrough

Case: Copy activity thành công nhưng Silver row count giảm 35%.

  1. Không publish Gold.
  2. So source count và Bronze count để loại trừ ingestion.
  3. So parse rejects, dedup và filter counts.
  4. Kiểm tra join loss theo key/null/reference data.
  5. Xác định code/config release gần nhất.
  6. Fix, rerun interval idempotently, reconcile rồi publish.

Pipeline status "Succeeded" ở từng activity không thay data quality gate.

16. Câu hỏi có đáp án

  1. Watermark nên lấy max(updated_at) từ source sau run không? Nên chốt upper bound trước extract; nếu không record phát sinh giữa run có thể bị skip.
  2. Copy activity có biến ADF thành compute engine? Không; nó chủ yếu move data, transform lớn nên giao engine phù hợp.
  3. Tại sao metadata-driven pipeline khó hơn lúc đầu? Cần contract/config validation và generic error handling, đổi lại scale nhiều entity nhất quán.
  4. Retry mọi lỗi schema có ích không? Không; lỗi permanent chỉ tốn thời gian và che incident.
