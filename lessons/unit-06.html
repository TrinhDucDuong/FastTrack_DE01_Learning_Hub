Trong bài này

1. Python của Data Engineer khác gì script thông thường?

Một pipeline tốt không chỉ "chạy được". Nó phải đọc dữ liệu lớn hợp lý, có thể rerun an toàn, cấu hình được, test được, quan sát được và không làm lộ secret.

Luồng cơ bản:

Extract -> Validate -> Transform -> Load -> Audit

2. Đọc dữ liệu theo streaming/chunk

Không đọc toàn bộ file lớn vào RAM nếu không cần.

import csv

with open("orders.csv", encoding="utf-8", newline="") as file:
    for row in csv.DictReader(file):
        process(row)

Với pandas có thể dùng pd.read_csv(..., chunksize=100_000). Với dữ liệu phân tích lớn, ưu tiên Parquet vì có schema, column pruning và nén tốt hơn CSV.

3. Generator và iterator

Generator trả từng phần tử, giúp giảm memory:

def valid_orders(rows):
    for row in rows:
        if row.get("order_id") and float(row["amount"]) >= 0:
            yield row

Pipeline có thể nối nhiều generator: read → validate → transform → write.

4. Validation và error handling

Phân loại lỗi:

  • Transient: timeout, rate limit, network chập chờn → retry có giới hạn và exponential backoff.
  • Permanent/data error: sai schema, ngày không hợp lệ → không retry mù; đưa vào quarantine/dead-letter.
  • Programming error: bug code → fail fast, log stack trace, sửa và deploy lại.

Không dùng except Exception: pass. Log tối thiểu: run_id, dataset, step, record key, error code; tránh log password/token/PII.

5. Idempotency và incremental load

Rerun cùng input phải không tạo record trùng.

  • Ghi đè partition của đúng ngày.
  • MERGE/UPSERT theo business key.
  • Lưu batch_id, checksum hoặc source offset đã xử lý.
  • Watermark: chỉ lấy dữ liệu mới hơn mốc trước, nhưng cần lookback window để bắt late-arriving data.

Ví dụ watermark an toàn hơn:

last_success = 2026-09-20 00:00
next_extract_from = last_success - 2 hours
deduplicate after load

Chỉ cập nhật watermark sau khi target commit thành công.

6. Cấu hình, secret và môi trường

  • Config không nhạy cảm: file cấu hình hoặc environment variable.
  • Secret: secret manager/managed identity; không hard-code và không commit Git.
  • Tách dev, test, prod; không dùng chung bucket/schema đích.
  • Pin dependency và ghi rõ phiên bản runtime.

7. Logging và metrics

Log có cấu trúc dễ tìm kiếm:

logger.info(
    "batch_completed",
    extra={"run_id": run_id, "rows_in": 1000, "rows_out": 998, "bad_rows": 2},
)

Metrics quan trọng: duration, rows read/written/rejected, bytes, retry count, freshness lag. Alert cả khi job "thành công" nhưng zero record hoặc volume lệch mạnh.

8. Test pipeline

  • Unit test: một hàm transform với input nhỏ và expected output.
  • Contract/schema test: tên cột, kiểu, required field.
  • Integration test: đọc/ghi với database hoặc storage test.
  • Data quality test: unique, not null, range, relationship.
  • Rerun test: chạy hai lần, kết quả không nhân đôi.

9. Cấu trúc project gợi ý

pipeline/
  src/
    extract.py
    transform.py
    load.py
    config.py
  tests/
  requirements.txt hoặc pyproject.toml
  README.md

Tách I/O khỏi business logic để hàm transform dễ test. Hàm nhỏ, input/output rõ ràng, type hint hợp lý.

10. Bài thực hành

Viết pipeline CSV → Parquet:

  1. Đọc theo chunk.
  2. Validate order_id, created_at, amount.
  3. Record lỗi ghi riêng cùng error_reason.
  4. Dữ liệu hợp lệ partition theo order_date.
  5. Log count và run_id.
  6. Chạy lại cùng file để chứng minh không trùng.

11. Checklist tự kiểm tra

  • File/connection luôn được đóng bằng context manager.
  • Timeout và retry chỉ áp dụng cho lỗi transient.
  • Không log secret hoặc PII thô.
  • Watermark chỉ advance sau khi thành công.
  • Có audit count và chiến lược quarantine/replay.

12. Schema-first thay vì "đọc gì cũng được"

Schema nên mô tả tên cột, type, nullable, domain, timezone và key. Infer schema tiện khi khám phá nhưng production có thể suy đoán khác giữa các batch (001 thành số 1, cột toàn null thành string...).

from dataclasses import dataclass
from datetime import datetime
from decimal import Decimal

@dataclass(frozen=True)
class Order:
    order_id: int
    customer_id: int
    created_at: datetime
    amount: Decimal

Tách parsing khỏi validation: parsing trả object hợp lệ hoặc error có code/cột/raw reference; không silently coerce giá trị mơ hồ.

13. Thời gian và timezone

  • Lưu timestamp sự kiện ở UTC khi có thể; giữ source timezone nếu cần audit.
  • Phân biệt event time, ingestion time và processing time.
  • Date partition theo business timezone cần ghi rõ, không dựa timezone của máy chạy.
  • DST làm một ngày có thể không đúng 24 giờ ở một số timezone.
from datetime import datetime, timezone

ingestion_ts = datetime.now(timezone.utc)

Không dùng naive datetime cho dữ liệu đi qua nhiều hệ thống.

14. Error record và quarantine

Một bad record hữu ích cần đủ để sửa/replay:

{
  "run_id": "run_20260922_01",
  "source_file": "orders_20260922.csv",
  "row_number": 18,
  "business_key": "order_99",
  "error_code": "INVALID_AMOUNT",
  "error_detail": "amount must be >= 0",
  "quarantined_at": "2026-09-22T03:00:00Z"
}

Raw payload nhạy cảm có thể lưu ở vùng bảo vệ thay vì log. Quarantine phải có owner, retention và quy trình reprocess; nếu chỉ tích tụ file lỗi thì chưa giải quyết vận hành.

15. Batch manifest

batch_id, source, extract_from, extract_to,
expected_files, received_files, source_rows,
valid_rows, rejected_rows, target_rows,
checksum, status, started_at, completed_at

Manifest là control plane cho dữ liệu: dùng phát hiện batch thiếu, ngăn process file dở, trace output và quyết định rerun.

16. Retry có kỷ luật

for attempt in range(max_attempts):
    try:
        return call_with_timeout()
    except TransientError:
        if attempt == max_attempts - 1:
            raise
        sleep(backoff(attempt) + jitter())

Phải có deadline tổng; nếu mỗi layer retry 3 lần, retry chồng có thể tạo rất nhiều request. Chọn một layer chịu trách nhiệm retry và phát metric số lần retry.

17. Worked example: incremental orders

  1. Đọc watermark thành công 10:00, chọn upper bound 11:00.
  2. Extract updated_at >= 09:50 AND updated_at < 11:00 để có lookback.
  3. Parse + validate; record lỗi vào quarantine.
  4. Deduplicate theo order_id, giữ updated_at mới nhất; tie-break bằng source sequence.
  5. MERGE staging vào target.
  6. Reconcile source/staging/target impacted keys.
  7. Commit watermark 11:00 sau thành công.

Nếu step 5 fail, watermark vẫn 10:00; rerun đọc lại overlap nhưng merge idempotent.

18. Câu hỏi có đáp án

  1. Tại sao Parquet nhanh cho analytics? Columnar, nén tốt, có schema và đọc đúng cột/row group cần thiết.
  2. Zero rejected rows có chắc tốt? Không; validator có thể chưa chạy hoặc rule quá lỏng.
  3. Khi nào fail toàn batch? Contract/schema lõi hỏng hoặc tỷ lệ lỗi vượt policy; record lỗi cô lập có thể quarantine.
  4. Watermark có thay backup không? Không; nó chỉ ghi tiến độ incremental.
