Distributed Processing with Spark & PySpark

Hiểu partition, lazy execution, shuffle, skew và hiệu năng phân tán.

SparkPartitionShuffleSkew

Trong bài này

1. Khi nào cần Spark?

Spark phù hợp khi dữ liệu/compute cần chia cho nhiều core hoặc nhiều máy, hoặc cần xử lý song song ở quy mô lớn. Với file nhỏ và logic đơn giản, Python/pandas/SQL có thể rẻ và dễ vận hành hơn.

2. Mental model

Driver -> lập kế hoạch job
  |
Cluster Manager -> cấp tài nguyên
  |
Executors -> chạy task trên các partition
  • Application gồm một driver và nhiều executor.
  • Job thường được tạo khi gọi action.
  • Stage bị chia tại ranh giới shuffle.
  • Task xử lý một partition trong một stage.
  • Partition là đơn vị dữ liệu để Spark xử lý song song.

3. Lazy evaluation

Transformation như select, filter, join chỉ tạo logical plan. Action như count, collect, write mới kích hoạt thực thi.

from pyspark.sql import functions as F

orders = spark.read.parquet("/bronze/orders")
daily = (
    orders.filter(F.col("status") == "Completed")
          .withColumn("order_date", F.to_date("created_at"))
          .groupBy("order_date")
          .agg(F.sum("amount").alias("revenue"))
)
daily.write.mode("overwrite").partitionBy("order_date").parquet("/gold/daily_revenue")

4. DataFrame và Spark SQL

DataFrame có schema nên Spark có thể tối ưu kế hoạch. DataFrame API và Spark SQL dùng cùng execution engine; chọn cách dễ đọc nhất cho team.

Ưu tiên built-in functions thay vì Python UDF vì optimizer hiểu được biểu thức built-in và tránh overhead serialize Python/JVM.

5. Narrow và wide transformation

  • Narrow: output partition phụ thuộc ít input partition, ví dụ filter, select.
  • Wide: dữ liệu phải đổi máy (shuffle), ví dụ groupBy, distinct, nhiều loại join.

Shuffle tốn network, disk và memory. Không phải bỏ hết shuffle, mà phải hiểu và giảm shuffle không cần thiết.

6. Join và data skew

  • Broadcast bảng dimension nhỏ để tránh shuffle bảng lớn.
  • Filter/select cột sớm để giảm dữ liệu trước join.
  • Kiểm tra key nóng: một key chiếm phần lớn record gây một task rất chậm.
  • repartition tạo shuffle; coalesce thường giảm partition với ít shuffle hơn.

Luôn kiểm tra execution plan bằng df.explain() và Spark UI trước khi tăng cluster.

7. Cache, partition và small files

  • Chỉ cache/persist DataFrame được tái sử dụng; cache cũng tốn tài nguyên.
  • Partition storage theo cột thường dùng để lọc và cardinality vừa phải, ví dụ order_date.
  • Không partition theo user_id hàng triệu giá trị.
  • Quá nhiều file nhỏ làm metadata/listing chậm; compact file theo lịch.
  • Không dùng collect() cho dữ liệu lớn vì kéo tất cả về driver.

8. Fault tolerance và rerun

Spark có thể chạy lại task mất dựa trên lineage, nhưng pipeline vẫn phải idempotent ở output. Job retry không tự đảm bảo dữ liệu không trùng. Cần overwrite đúng partition, transactional table hoặc MERGE theo key.

10. Bài thực hành PySpark

Từ orders và order_items:

  1. Ép schema rõ ràng, không dựa hoàn toàn vào infer schema.
  2. Lọc order completed.
  3. Join, tính revenue theo ngày và category.
  4. Kiểm tra row count trước/sau join để phát hiện nhân bản.
  5. Dùng explain, nhận diện shuffle.
  6. Ghi Parquet partition theo ngày và tránh file quá nhỏ.

11. Checklist tự kiểm tra

  • Biết grain và schema trước transform.
  • Không collect() dữ liệu lớn.
  • Built-in expression được ưu tiên hơn Python UDF.
  • Kiểm tra skew/shuffle trước khi scale compute.
  • Output rerun an toàn và có kiểm tra count.

Tài liệu chính: Spark SQL và DataFrames.

12. Từ logical plan đến physical plan

Spark phân tích expression/schema, tối ưu logical plan rồi chọn physical operators. df.explain("formatted") giúp thấy scan, filter, exchange/shuffle, join và aggregate.

FileScan parquet
  -> Filter status = Completed
  -> Exchange hashpartitioning(customer_id)   # shuffle boundary
  -> HashAggregate

Predicate pushdown và column pruning giảm dữ liệu từ lúc scan. UDF mờ với optimizer có thể làm mất cơ hội tối ưu.

13. Join strategy

  • Broadcast hash join: gửi bảng nhỏ tới executors; tránh shuffle bảng lớn nhưng bảng broadcast phải vừa memory.
  • Sort-merge join: hai phía shuffle/sort theo key; phù hợp equi-join lớn.
  • Shuffle hash join: build hash table theo partition; nhạy với memory/skew.

Không ép broadcast chỉ vì dimension "có vẻ nhỏ"; kiểm tra kích thước sau filter và threshold/runtime.

14. Data skew bằng ví dụ

Nếu 40% events có customer_id = null, hash partition dồn chúng vào một task. Dấu hiệu: đa số task hoàn tất nhanh nhưng một vài task rất lâu/oom.

Các hướng xử lý:

  • Tách null/khóa nóng xử lý riêng.
  • Pre-aggregate trước join.
  • Broadcast phía nhỏ.
  • Salting key cho key nóng rồi aggregate lại.
  • Bật/tận dụng adaptive query execution nếu platform hỗ trợ, nhưng vẫn đo.

Salting tăng complexity và có thể nhân bản dimension; chỉ dùng sau khi xác nhận skew.

15. Partition in-memory khác partition on storage

Spark partition là đơn vị task runtime. Storage partition là folder/pruning layout. Đọc một folder ngày có thể tạo nhiều Spark partitions dựa trên file size. partitionBy("order_date") khi ghi không đảm bảo mỗi ngày đúng một file.

repartition(n, key) shuffle và cân lại; coalesce(n) thường chỉ giảm số partition, có thể mất cân bằng. Số partition tốt phụ thuộc data size, cluster, operator và target file size.

16. Fault tolerance không thay idempotency

Executor chết: Spark có thể rerun task từ lineage. Nhưng nếu task đã gọi API bên ngoài hoặc append sink trước khi chết, side effect có thể lặp. Tránh external side effect trong row UDF; output dùng staging/transactional commit hoặc overwrite partition deterministic.

17. Worked example: tối ưu daily revenue

  1. Chỉ đọc partition 7 ngày cần recompute.
  2. Select cột order/item cần thiết.
  3. Filter completed trước join.
  4. Broadcast dim_product nếu đủ nhỏ.
  5. Aggregate theo order_date, category.
  6. Repartition hợp lý theo output date và ghi staging.
  7. Validate totals, rồi publish/replace impacted partitions.

Đo input bytes, shuffle read/write, task duration distribution và output file count trước/sau; không dùng cảm giác.

18. Câu hỏi có đáp án

  1. Transformation nào luôn tạo shuffle? Grouping và repartition thường có; join có thể tránh shuffle một phía bằng broadcast.
  2. Cache càng nhiều càng tốt? Không; cache chiếm memory và có cost materialize/evict.
  3. Vì sao collect() nguy hiểm? Dồn toàn bộ output về driver, có thể OOM.
  4. Tăng executor có chữa skew không? Thường không chữa key nóng; một partition vẫn do một task xử lý.
