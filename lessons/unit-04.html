Thiết kế API cốt lõi

1. Mục tiêu

Thiết kế REST API có contract rõ, validation, authentication/authorization, idempotency, pagination, error model, timeout, test và observability.

2. Request lifecycle

Client -> middleware -> authentication -> validation -> route
       -> service/business rule -> repository/downstream
       -> response serialization -> middleware/log/metrics

Route nên mỏng: nhận transport data, gọi service và map kết quả/lỗi. Business rule không nên nằm rải trong router.

3. Resource và HTTP method

  • GET /products/{id}: đọc, safe và idempotent.
  • POST /orders: tạo resource; có thể cần idempotency key.
  • PUT /users/me: thay toàn bộ representation theo contract.
  • PATCH /orders/{id}/status: sửa một phần/transition.
  • DELETE: nên định nghĩa rõ hard delete, soft delete hay deactivate.

Status thường dùng: 200, 201 + Location, 204, 400, 401, 403, 404, 409, 422, 429, 500/502/503. Không dùng 200 cho mọi lỗi.

4. Pydantic schema và boundary validation

from decimal import Decimal
from pydantic import BaseModel, Field

class OrderItemCreate(BaseModel):
    product_id: int = Field(gt=0)
    quantity: int = Field(gt=0, le=100)

class OrderCreate(BaseModel):
    items: list[OrderItemCreate] = Field(min_length=1, max_length=50)
    coupon_code: str | None = Field(default=None, max_length=40)

class OrderRead(BaseModel):
    id: int
    status: str
    total_amount: Decimal

Schema validation kiểm tra shape/type/range. Rule "coupon thuộc user và còn hạn" là business validation trong service với dữ liệu database.

5. Dependency injection và lifecycle

from fastapi import APIRouter, Depends, status

router = APIRouter(prefix="/api/v1/orders", tags=["orders"])

@router.post("", response_model=OrderRead, status_code=status.HTTP_201_CREATED)
def create_order(payload: OrderCreate, service=Depends(get_order_service)):
    return service.create(payload)

Database pool/HTTP client nên mở ở application lifespan và đóng khi shutdown. Dependency theo request có thể cấp session/transaction nhưng không tạo engine mới mỗi lần.

6. Error contract

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "One or more products are out of stock.",
    "details": [{"product_id": 42, "available": 1}],
    "correlation_id": "req_01..."
  }
}

code ổn định cho client; message dễ hiểu; details không lộ SQL/stack/secret. Map domain exception tập trung bằng exception handler.

7. Idempotency cho checkout/payment

Client gửi Idempotency-Key. Server lưu key + request fingerprint + kết quả trong transaction phù hợp:

  1. Key mới: xử lý và lưu response.
  2. Key cũ + cùng payload: trả lại kết quả cũ.
  3. Key cũ + payload khác: trả conflict.
  4. Hai request đồng thời: unique constraint/lock đảm bảo chỉ một request thắng.

Key có TTL và scope theo user/endpoint. Chỉ thêm header mà không có storage/atomicity chưa tạo idempotency.

8. Pagination và filter

Offset pagination dễ làm nhưng chậm/không ổn định ở offset lớn khi data thay đổi. Cursor/keyset pagination dùng sort key ổn định:

WHERE (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT :limit

Giới hạn limit, whitelist sort/filter field và luôn có tie-breaker unique.

9. Authentication và authorization

  • Authentication xác định identity; authorization kiểm tra action/resource.
  • 401: chưa/xác thực không hợp lệ; 403: đã xác thực nhưng không có quyền.
  • Không tin user_id từ payload nếu đã có identity trong token/session.
  • Admin route cần policy/role rõ và audit thay đổi nhạy cảm.
  • CORS không phải authentication; nó là browser policy.

10. Timeout, retry và rate limit

API gọi downstream phải có timeout nhỏ hơn timeout toàn request. Retry chỉ transient error, có backoff/jitter và tôn trọng deadline. Rate limit bảo vệ tài nguyên nhưng cần trả 429 và Retry-After khi phù hợp.

Payload size limit, request body streaming và batch max size ngăn một request chiếm hết memory.

11. Test strategy

  • Unit test service với fake repository.
  • API test status/schema/header/error.
  • Integration test database transaction/constraint.
  • Contract test downstream.
  • Security test: missing token, role sai, object-level access.
  • Idempotency/concurrency test: hai request cùng key.

12. Observability

Log method, route template, status, latency, correlation ID và caller/client class; không dùng raw URL nếu chứa PII. Metrics: request rate, error rate, latency percentile, saturation và downstream dependency.

13. Mini lab

Xây POST /api/v1/orders và GET /api/v1/orders:

  1. Schema và business validation tách biệt.
  2. Transaction tạo order/items.
  3. Idempotency key cho create.
  4. Cursor pagination cho list.
  5. Error contract thống nhất.
  6. Test duplicate request, out-of-stock và unauthorized access.

14. Câu hỏi có đáp án

  1. Validation pass có nghĩa business hợp lệ không? Không; schema đúng chưa chứng minh stock/coupon/ownership đúng.
  2. Vì sao retry POST nguy hiểm? Có thể tạo side effect trùng nếu không idempotent.
  3. CORS có bảo vệ API khỏi curl không? Không; curl không bị browser CORS policy.
  4. Vì sao log route template thay raw path? Tránh cardinality cao và lộ ID/PII.
