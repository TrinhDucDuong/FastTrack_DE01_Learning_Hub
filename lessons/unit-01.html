Version Control with Git

Quản lý thay đổi như các snapshot có thể review, truy vết và phục hồi.

GitBranchPull RequestRecovery

Trong bài này

1. Mental model

Working directory -> git add -> Staging area -> git commit -> Local repository
                                                        -> git push -> Remote
  • Commit: snapshot có ID, author, time và parent.
  • Branch: con trỏ tới một chuỗi commit; HEAD là vị trí hiện tại.
  • Remote: repository ở server, thường tên origin.
  • Working tree / staging: thay đổi đang làm / phần sẽ vào commit kế tiếp.

2. Workflow cơ bản

git status
git switch -c feature/orders-ingestion
git add path/to/file.py
git diff --staged
git commit -m "Add incremental orders ingestion"
git fetch origin
git rebase origin/main
git push -u origin feature/orders-ingestion

Luôn xem git status và git diff trước commit. Add đúng file thay vì git add . khi workspace có thay đổi không liên quan.

3. Commit tốt và an toàn

  • Một commit giải quyết một ý logic; message nói rõ intent.
  • Không trộn format toàn project với feature nhỏ.
  • Không commit secret, .env, output data lớn hoặc virtual environment.
  • .gitignore chỉ ngăn file chưa tracked; không xóa secret khỏi history.
  • Nếu secret đã commit: revoke/rotate ngay, sau đó xử lý history theo quy trình team.

4. Merge, rebase và conflict

  • Merge kết hợp lịch sử và có thể tạo merge commit.
  • Rebase đặt commit của mình lên base mới; lịch sử gọn nhưng commit ID đổi.
  • Không rebase/force-push branch dùng chung nếu chưa thống nhất.

Khi conflict: đọc intent hai phía → sửa kết quả đúng → chạy test → git add → git rebase --continue hoặc commit merge.

5. Pull request

PR nên có vấn đề/phạm vi, cách test, ảnh hưởng schema/data/downstream, migration và rollback/recovery. Reviewer kiểm tra correctness, security, maintainability và operational risk; không chỉ style.

6. Lệnh cứu hộ

git diff
git diff --staged
git log --oneline --graph --decorate -20
git restore --staged file
git stash push -m "wip"
git reflog
git revert <commit>

reset --hard, clean và force push có thể làm mất thay đổi; chỉ dùng khi hiểu chính xác target và policy.

7. Git cho Data Engineering

Version control SQL/dbt, DAG, Spark/Python, schema contract, tests, IaC và config không nhạy cảm. Dataset lớn để trong object storage/artifact system. Schema migration phải đi cùng thứ tự deploy và compatibility plan. Tag/release ID nên xuất hiện trong pipeline log để biết code nào tạo dataset.

8. Bài thực hành và checklist

Tạo feature branch, chia thay đổi thành hai commit, tạo/resolve một conflict, rebase lên main, chạy test và mở PR. Sau đó thử git revert trên nhánh demo.

  • Phân biệt working tree, staging, commit và remote.
  • Commit nhỏ, rõ và không có secret/data lớn.
  • Biết merge/rebase khác nhau ở đâu.
  • Resolve conflict xong luôn chạy test.
  • PR nêu data/schema impact và recovery.

9. Giải thích sâu: Git thật sự lưu gì?

Git không lưu một chuỗi "dòng đã sửa" như cách ta thường hình dung. Mỗi commit trỏ tới một cây thư mục (tree), metadata và commit cha. File content được lưu dưới dạng object có hash. Vì commit chứa hash của parent, lịch sử tạo thành một đồ thị bất biến tương đối: đổi nội dung hoặc parent sẽ tạo commit ID khác.

Điều này giải thích ba hiện tượng:

  • Branch rất nhẹ vì chủ yếu là một con trỏ tới commit.
  • Rebase tạo commit ID mới vì parent thay đổi, dù nội dung nhìn giống nhau.
  • Detached HEAD nghĩa là HEAD trỏ thẳng commit thay vì branch; commit mới có thể khó tìm nếu không tạo branch.

10. Fetch, pull và push theo ví dụ

Giả sử local có main, remote-tracking branch là origin/main:

git fetch  = cập nhật hiểu biết local về remote, chưa sửa working branch
git merge origin/main = nhập lịch sử remote vào branch hiện tại
git pull   = fetch + merge (hoặc rebase tùy config)
git push   = đề nghị remote cập nhật ref nếu lịch sử hợp lệ

Workflow an toàn khi đang làm feature:

git status
git fetch origin
git rebase origin/main
# resolve conflict + test
git push --force-with-lease  # chỉ khi feature branch riêng đã rebase

--force-with-lease vẫn là force push nhưng từ chối ghi đè nếu remote đã có commit mình chưa thấy. Nó không biến force push thành hoàn toàn an toàn.

11. Worked example: sửa pipeline bằng hai commit

Yêu cầu: thêm validation amount >= 0 và test.

  1. Commit 1 chỉ thêm validation + unit test.
  2. Commit 2 thêm metric invalid_amount_count + documentation.
  3. PR giải thích record lỗi bị quarantine, không bị âm thầm bỏ.
  4. Reviewer có thể revert riêng metric mà không mất bug fix.

Nếu gộp refactor, đổi format, validation và dashboard vào một commit, review khó và rollback mang theo thay đổi không liên quan.

12. Tình huống production

Lỡ commit secret

  1. Xem secret như đã bị lộ, kể cả repository private.
  2. Revoke/rotate credential trước.
  3. Tìm nơi secret được dùng và theo dõi access log.
  4. Xóa khỏi history bằng công cụ/quy trình của team nếu cần.
  5. Thêm secret scanning và pre-commit/CI check để ngăn tái diễn.

Commit tốt nhưng pipeline production lỗi

Dùng git revert tạo commit đảo thay đổi trên branch chung. Không rewrite lịch sử production branch. Nếu pipeline đã ghi dữ liệu sai, revert code chưa đủ: cần xác định partition bị ảnh hưởng, restore/recompute và đối soát lại.

13. Câu hỏi tự kiểm tra có đáp án

  1. Vì sao git fetch an toàn để kiểm tra trước? Vì nó cập nhật remote-tracking refs mà không merge vào working branch.
  2. Vì sao rebase branch chung nguy hiểm? Nó thay commit ID, khiến lịch sử của người khác phân kỳ.
  3. Khi nào dùng revert? Khi commit đã chia sẻ và cần đảo bằng một thay đổi có audit trail.
  4. Git có phù hợp lưu file Parquet 10 GB không? Không; lưu data ở object storage và version metadata/manifest trong Git.
