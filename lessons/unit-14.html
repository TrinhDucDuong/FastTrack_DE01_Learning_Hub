Advanced Orchestration with Airflow

Biến dependency, schedule, retry và backfill thành workflow-as-code.

AirflowDAGData IntervalBackfill

Trong bài này

1. Airflow làm gì?

Airflow xây và chạy workflow theo DAG (Directed Acyclic Graph). DAG mô tả task, dependency, schedule, retry và operational metadata. Airflow là orchestrator; không nên nhét dữ liệu lớn vào chính metadata database hoặc XCom.

Dag processor parses DAGs -> metadata database
Scheduler finds ready tasks -> Executor -> Workers run tasks
API/UI shows state and supports operations
Triggerer handles deferred work (khi dùng)

Thành phần cụ thể thay đổi theo major version/deployment, nên luôn đối chiếu docs đúng version đang cài.

2. Khái niệm quan trọng

  • DAG: workflow không có vòng lặp dependency.
  • Task: đơn vị công việc.
  • DAG Run / Task Instance: lần chạy cụ thể.
  • Data interval: khoảng dữ liệu mà một run chịu trách nhiệm.
  • Operator/TaskFlow task: template để thực hiện task.
  • Sensor: đợi điều kiện/sự kiện; ưu tiên deferrable khi chờ lâu.
  • XCom: metadata nhỏ giữa task; không truyền DataFrame/file lớn.
  • Connection/Variable: cấu hình runtime; secret cần backend phù hợp.
  • Pool: giới hạn concurrency với hệ thống downstream.

3. Lịch và data interval

DAG daily thường chạy sau khi khoảng ngày đã kết thúc để dữ liệu đủ. Ví dụ run mang logical date/ngày dữ liệu D không nhất thiết bắt đầu lúc đầu ngày D.

Không dùng datetime.now() làm start_date. Task phải đọc data_interval_start/end hoặc parameter được truyền, không đoán theo giờ máy chạy; như vậy backfill mới đúng.

4. DAG tối giản

Ví dụ theo cú pháp Airflow 3; Airflow 2 có import path khác:

from datetime import datetime, timedelta
from airflow.sdk import dag, task

@dag(
    schedule="@daily",
    start_date=datetime(2026, 1, 1),
    catchup=False,
    max_active_runs=1,
    tags=["sales"],
)
def sales_daily():
    @task(retries=2, retry_delay=timedelta(minutes=1))
    def ingest():
        return {"manifest_path": "/audit/run.json"}

    @task
    def transform(metadata: dict):
        print(metadata["manifest_path"])

    transform(ingest())

sales_daily()

Import path có thể khác giữa các major version. Mục tiêu ví dụ là dependency và chỉ truyền metadata nhỏ.

5. Idempotency, retry và timeout

  • Task ghi vào partition/data interval xác định.
  • Dùng staging + atomic publish/merge.
  • Retry chỉ lỗi transient; giới hạn số lần và có backoff.
  • execution_timeout ngăn task treo vô hạn.
  • API call có network timeout riêng.
  • Ghi run_id, data interval và target trong log.

Task extract -> transform -> load nên độc lập, rerun task nào cũng không phá kết quả đã đúng.

6. Catchup, backfill và late data

  • catchup: scheduler tạo run cho các interval cũ chưa chạy.
  • backfill: chủ động chạy lại nhiều interval lịch sử.
  • Hạn chế concurrency bằng pool/max active runs để không đánh sập source/sink.
  • Backfill phải dùng cùng logic production nhưng ghi đúng interval.
  • Late data có thể cần lookback/recompute window.

Test backfill nhỏ trước; quan sát cost và downstream rate limit.

7. Dynamic task mapping và TaskGroup

  • Dynamic mapping tạo task theo danh sách runtime, ví dụ danh sách bảng.
  • TaskGroup giúp UI dễ đọc nhưng không phải isolation boundary.
  • Tránh tạo hàng chục nghìn task nhỏ; orchestration overhead có thật.
  • Không gọi API/database nặng ở top-level DAG vì Dag processor parse file thường xuyên.

8. Vận hành production

  • DAG code qua Git/CI, parse test và unit test.
  • Secret ở secret backend, không trong DAG/Variable plaintext nếu tránh được.
  • Alert failed task, missed deadline, zombie/heartbeat và queue delay.
  • Log phải tập trung và truy cập được sau khi worker mất.
  • Chọn executor/deployment theo workload, isolation và quy mô; không scale trước khi đo.

9. Bài thực hành

Viết DAG orders_daily:

  1. Sensor đợi file hoàn chỉnh.
  2. Ingest Bronze theo data_interval.
  3. Chạy quality gate.
  4. Trigger Spark/dbt transformation.
  5. Refresh semantic/report sau khi Gold pass.
  6. Ghi audit và callback alert khi fail.
  7. Backfill 3 ngày và chứng minh không trùng.

10. Checklist

  • DAG import nhanh, không thực hiện I/O ở top level.
  • Task nhỏ vừa đủ, retry/rerun an toàn.
  • Dùng data interval, không dùng thời gian hiện tại để chọn dữ liệu.
  • XCom chỉ chứa metadata nhỏ.
  • Có pool/concurrency, timeout, alert và runbook.

Tài liệu chính: Airflow core concepts, Airflow scheduler.

11. Data interval bằng timeline

DAG @daily xử lý ngày 2026-09-21 có interval [2026-09-21 00:00, 2026-09-22 00:00). Scheduler thường tạo run sau khi interval kết thúc. Task query:

WHERE event_time >= :data_interval_start
  AND event_time <  :data_interval_end

Dùng khoảng half-open tránh overlap ở biên. Backfill ngày cũ vẫn lấy đúng interval; dùng now() sẽ lấy nhầm dữ liệu ngày chạy backfill.

12. Operator, Sensor và TaskFlow chọn gì?

  • Operator/provider có sẵn phù hợp khi chỉ cần cấu hình call đến service.
  • TaskFlow thuận tiện viết Python task và dependency rõ.
  • Sensor chờ condition; mode reschedule/deferrable giải phóng worker slot tốt hơn poke giữ slot lâu.
  • Task chỉ trigger job external chưa đủ: cần sensor/deferrable wait và kiểm tra final state nếu downstream async.

13. Trigger rule và cleanup

Mặc định downstream chạy khi upstream success. Cleanup/audit có thể cần chạy dù upstream fail, nhưng trigger rule sai có thể biến DAG run thành success giả. Tách:

  • Task nghiệp vụ bắt buộc.
  • Task audit/notify luôn chạy.
  • DAG status/quality gate phản ánh đúng outcome nghiệp vụ.

14. XCom và data passing

XCom dành cho ID/path/count/small metadata. Pattern:

ingest returns {manifest_uri, batch_id, rows}
transform reads data from manifest_uri/object storage

Không serialize DataFrame hoặc hàng MB dữ liệu vào metadata database. Data đi qua storage/warehouse; control metadata đi qua XCom.

15. DAG test strategy

  • Import/parse test: không syntax/import error, DAG ID/task ID đúng.
  • Unit test callable/business logic ngoài DAG.
  • Structure test: dependency, schedule, retries, pool.
  • Integration test provider/connection ở non-prod.
  • Backfill test một vài interval, kể cả zero/late data.

DAG file top-level phải parse nhanh và deterministic. Không query database/list cloud files lúc import.

16. Failure walkthrough

Task transform fail sau khi ingest thành công:

  1. Airflow retry transform nếu lỗi transient; không tự rerun ingest nếu dependency không bị clear.
  2. Transform đọc manifest/output Bronze deterministic.
  3. Sau fix, clear đúng task instance và downstream cho interval.
  4. Quality gate + publish chạy lại idempotently.
  5. Audit ghi attempt và final result; không xóa dấu vết fail.

17. Câu hỏi có đáp án

  1. Airflow có phải streaming engine? Không; nó orchestration batch/workflow, không xử lý event record liên tục.
  2. catchup=False có nghĩa không backfill được? Không; vẫn có thể trigger/backfill chủ động.
  3. Vì sao task quá nhỏ có hại? Scheduler/metadata/log overhead tăng và DAG khó vận hành.
  4. Retry ở Airflow có thay retry HTTP client? Không hoàn toàn; task retry chạy lại toàn task, network retry xử lý call transient nhỏ với deadline.
