Relational Databases & Advanced SQL

Hiểu transaction, index, execution plan và cách viết SQL phân tích.

SQLACIDIndexWindow Function

Trong bài này

1. Mục tiêu

Sau bài này, bạn cần thiết kế bảng OLTP cơ bản, giải thích ACID/index/query plan, viết join/aggregate/window function đúng grain và nhận diện race condition.

2. Relational model và constraint

  • Table đại diện một loại entity hoặc relationship.
  • Primary key định danh duy nhất một row.
  • Foreign key bảo vệ quan hệ giữa bảng.
  • NOT NULL, UNIQUE, CHECK đưa invariant quan trọng xuống database.
  • Constraint không thay validation ở API; hai lớp bảo vệ các boundary khác nhau.

Ví dụ:

CREATE TABLE orders (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    status VARCHAR(20) NOT NULL
        CHECK (status IN ('Pending', 'Paid', 'Cancelled')),
    total_amount DECIMAL(18, 2) NOT NULL CHECK (total_amount >= 0),
    created_at TIMESTAMP NOT NULL,
    updated_at TIMESTAMP NOT NULL
);

3. Normalization thay vì chỉ nhớ 1NF/2NF/3NF

Mục tiêu normalization là giảm update anomaly và giữ một fact nghiệp vụ ở một nơi.

  • 1NF: mỗi cell có giá trị nguyên tử theo model; không lưu danh sách product ID bằng chuỗi 1,2,3.
  • 2NF: với composite key, non-key column phụ thuộc toàn bộ key. Trong order_items(order_id, product_id, product_name), product_name chỉ phụ thuộc product_id, nên thuộc bảng products.
  • 3NF: non-key column không phụ thuộc bắc cầu qua non-key khác. orders(user_id, user_city) dễ stale vì city phụ thuộc user.

Denormalization là quyết định có chủ đích để tối ưu đọc, kèm cơ chế giữ dữ liệu đồng bộ; không phải "bỏ normalization cho nhanh".

4. ACID bằng tình huống thanh toán

  • Atomicity: tạo payment và đổi order status cùng thành công hoặc rollback.
  • Consistency: constraint/invariant đúng trước và sau transaction.
  • Isolation: hai checkout đồng thời không bán cùng đơn/tồn kho sai.
  • Durability: đã commit thì vẫn tồn tại sau restart theo guarantee của hệ thống.

Isolation level kiểm soát hiện tượng đọc đồng thời như dirty read, non-repeatable read và phantom. Isolation mạnh hơn thường đánh đổi concurrency; chọn theo invariant và DB engine.

5. Index hoạt động và vì sao không tạo thật nhiều

B-tree giữ key có thứ tự và pointer tới row/page. Index hữu ích cho equality, range, join và order theo prefix phù hợp.

Composite index (status, created_at) hỗ trợ:

WHERE status = 'Paid' AND created_at >= :start

nhưng thường không tối ưu chỉ WHERE created_at >= :start vì left-most prefix. Index tốn storage, tăng write cost và maintenance. Cột boolean ít selective hiếm khi đáng index đơn lẻ.

Covering index chứa đủ cột query cần, giảm lookup về bảng nhưng làm index lớn. Luôn xác nhận bằng execution plan và workload thực.

6. Logical query processing order

FROM/JOIN -> ON -> WHERE -> GROUP BY -> HAVING
-> SELECT -> DISTINCT -> ORDER BY -> LIMIT

Điều này giải thích vì sao alias tạo ở SELECT thường chưa dùng được trong WHERE, và vì sao filter trước aggregate đặt ở WHERE, filter sau aggregate đặt ở HAVING.

7. JOIN và lỗi nhân bản measure

SELECT o.id, SUM(oi.quantity * oi.unit_price) AS revenue
FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE o.status = 'Paid'
GROUP BY o.id;

Trước join phải biết cardinality: 1:1, 1:N hay N:N. Nếu join thêm payments (một order có nhiều payment attempt), mỗi item có thể bị lặp. Giải pháp thường là aggregate payment về một row/order trước khi join hoặc join đúng record thành công.

8. Window function

Window function không làm mất row như GROUP BY:

SELECT
    user_id,
    id AS order_id,
    created_at,
    LAG(created_at) OVER (
        PARTITION BY user_id ORDER BY created_at
    ) AS previous_order_at,
    ROW_NUMBER() OVER (
        PARTITION BY user_id ORDER BY created_at DESC
    ) AS recency_rank
FROM orders
WHERE status = 'Paid';

ROW_NUMBER luôn đánh số duy nhất; RANK để hở hạng khi tie; DENSE_RANK không để hở.

9. CTE, subquery và query rewrite

CTE chủ yếu giúp biểu đạt logic; có materialize hay inline phụ thuộc engine/version. Query rewrite thực tế:

  • Chỉ select cột cần, tránh SELECT *.
  • Filter sớm khi không đổi semantics.
  • Tránh function/cast trên indexed column trong predicate nếu có thể.
  • Thay correlated subquery chạy lặp bằng join/window khi hợp lý.
  • Aggregate về đúng grain trước khi join.
  • Dùng EXPLAIN/actual plan thay vì đoán optimizer.

Ví dụ predicate dễ dùng index hơn:

-- Tránh: WHERE DATE(created_at) = '2026-09-22'
WHERE created_at >= '2026-09-22'
  AND created_at <  '2026-09-23'

10. Concurrency control

  • Pessimistic lock: khóa trước khi sửa; rõ ràng nhưng có wait/deadlock.
  • Optimistic lock: update kèm version; nếu zero row affected thì có conflict.
UPDATE products
SET stock = stock - :qty,
    version = version + 1
WHERE id = :id
  AND version = :expected_version
  AND stock >= :qty;

Nếu affected rows = 0, dữ liệu đã đổi hoặc tồn kho thiếu; application phải xử lý, không coi là success.

11. Đọc execution plan

Tìm scan/seek, estimated vs actual rows, join algorithm, sort/hash spill và predicate. Ước lượng sai lớn có thể đến từ statistics cũ hoặc data skew. Đừng kết luận "scan luôn xấu": đọc phần lớn bảng thì sequential scan có thể rẻ hơn nhiều random lookup.

12. Mini lab

  1. Tạo users, orders, order_items, products có constraint.
  2. Query top 2 product/category bằng DENSE_RANK.
  3. Tính thời gian giữa hai lần mua bằng LAG.
  4. Tạo index phục vụ orders paid theo khoảng ngày và xem plan trước/sau.
  5. Cố ý join thêm payment attempts, phát hiện double count rồi sửa.

13. Câu hỏi có đáp án

  1. Index làm query đọc nhanh nhưng đổi lại gì? Storage, write/maintenance cost và optimizer complexity.
  2. WHERE khác HAVING? WHERE lọc row trước grouping; HAVING lọc group sau aggregate.
  3. Vì sao DISTINCT không phải cách sửa join tốt? Nó che sai cardinality và có thể xóa row hợp lệ, đồng thời tốn sort/hash.
  4. Khi nào optimistic locking hợp lý? Conflict hiếm và không muốn giữ lock lâu.
